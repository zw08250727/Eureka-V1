# PM 协作与统一评审

## 主责与来源

`modules.json` 指定模块、公共规则、代码目录、关联模块及负责人。2026-10-16 已提供的分工同步至模块清单和 PRD 顶部；跨市场分工不同的模块分别标注国内与海外主责，未指派范围保留“待认领”。“鹤飞”与“李鹤飞”暂按原指派保留，是否同一人待确认；支付主责与市场范围待确认。模块 PM 联合维护共用规则和两地差异，不各自复制完整工程。账号／工作区／权限仍有独立主责待认领；张伟负责架构和 UI，不自动代领其他专项或代签评审。

PM 使用短期分支协作，合入前核对最新变更；发生冲突按规则含义合并，禁止整文件覆盖他人的修订。

## 每次变更必须交付

1. 问题、目标、模块主责和适用市场／个人团队范围。
2. 修改的规则 ID、国内／海外差异、是否影响共享业务基线。
3. 可操作原型入口；必要截图和失败、权限、恢复状态。
4. 上游输入、下游输出、影响模块与联合评审人。
5. Given / When / Then 验收证据、待确认参数、回滚方式。
6. 复用／新增组件清单及职责，市场差异位于主题、配置还是业务适配；加载、空、失败、无权限、只读和恢复状态。

使用 [PM 迭代模板](pm-change-template.md)。可操作交付必须是现有 React 路由，遵守 [FE-01～FE-10](frontend.md)，不能以单文件 HTML 或 iframe 演示替代。业务规则编号继续来自 business-baseline.md；FE 编号是工程规则，不覆盖业务决策。

先评审需求与组件方案，再实施、验证和合入；仅确认文档或本地修改不代表授权发布。检查例外、冻结基线变更须说明具体位置、主责角色和退出条件，不能直接更新指纹让检查通过。负责人未认领时保持“待认领”，不得虚构人名或把自动测试视为人工签署。

分支建议 `codex/<module>-<change>`。流程：草稿 → 模块自检 → 依赖方评审 → 统筹确认 → 合入 develop → CI／Pages → 核对发布快照。这里的人工评审状态不能由“存在测试文件”推定通过。

## 统一检查

| 链路 | 核对点 |
| --- | --- |
| 注册→邀请→团队 | 市场域一致、最多一个 Team、身份及席位正确 |
| 支付→订阅→Credits | 成功后生效、幂等、失败和重试不重复发放、归属不串区 |
| Agent→连接器→用量 | 使用发起时配置与授权、断连不可继续调用、所属区计费 |
| 会议→待办→日历 | 人工确认、稳定来源、共享权限独立重检、编辑同步 |
| 到期／移除／撤权 | 页面、Agent 和连接器同步拒绝后续操作，历史数据按规则保留 |
| 国内↔海外 | 两地登录态、账号、订单、余额、配置、数据互不串用 |

`/review/` 汇总配置差异、模块依赖和待确认事项。自动化只能验证明确断言、结构和依赖；标准是否合理、差异是否被允许由模块主责及统筹人判断。

## 发布与交接

`npm run package:markets` 从同一次构建生成国内、海外静态包及 manifest。交付核对源码提交、是否有未提交修改和规则／配置版本；两包保留固定市场路径，每包根入口进入对应版本。需要静态 HTTP 服务，不通过 file:// 打开 Next.js 导出文件。

正式分发前保留通过的检查报告，并指定 PM 姓名、正式主题、渠道、价格和 Agent 服务配置。不要把演示价格、OAuth 或支付结果标为生产能力。

## 市场专项 PRD 的维护边界

现有 PRD 独立设置“国内专项 PRD”和“海外专项 PRD”。国内 PM 维护 `cn-*` 章节，海外 PM 维护 `global-*` 章节；同一市场的个人／团队差异在该章节标注。详细商品、渠道、有效期、目录与独立实现只在所属市场章节维护，共用章节保留归属、权限、状态和幂等契约。

每轮注明规则 ID、负责人、源码／配置版本、变更是配置还是流程／模型、上下游影响及 Given／When／Then 验收；区分产品目标、已实现原型与真实服务依赖。共享契约变化需双方联合评审，不能以另一市场代码现状自动决定本市场需求。

同一网站各章节可独立编辑并复制稳定锚点。源码仍集中为 `src/prototype/prd/content.json`；合并时按章节 ID 处理，禁止用个人导出的整稿覆盖其他市场更新。正式发布仍遵循本文件的统一发布检查，不因拆分章节而自动部署。
